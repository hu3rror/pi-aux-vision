# Vision gating: describe_image only for session models without image input

`describe_image` used to be declared to the session model whenever the plugin was enabled and an auxiliary vision model was configured — even when the current session model natively supports image input. A vision-capable main model then competes with the aux-vision route (duplicate capability, an extra round-trip to a different model, and a transcription contract designed for blind reasoning) instead of reading images natively. The tool is now only declared to the session model when the plugin is enabled, an auxiliary vision model is configured and available, **and** the current session model lacks image input; visibility re-evaluates on `session_start` and `model_select`.

**Considered Options**:

- Always active when configured (status quo): one tool path for every model, but vision-capable sessions get a redundant competing route.
- Strict gating (chosen): the tool's visibility is computed by a single sync point (enabled && configured && current model defined && not vision-capable) driven by `session_start`, `model_select`, and the `/vision` commands. An undefined model at session start defers to `model_select`. Auto-discovery of an unconfigured aux model runs only in blind sessions, so vision-capable sessions stay quiet (no config write, no notification). An explicit `/vision enable` does not override gating; instead the feedback states that the tool stays non-intervening, and `/vision status` surfaces the gating state.
- Gating with an escape-hatch config flag (`interveneOnlyWhenBlind`, default true): flexibility for users who prefer aux vision even with a vision-capable main model; rejected to keep the config surface minimal and the behavior a single rule.

**Consequences**: vision-capable sessions never see `describe_image` — images are read natively (attached image content or the built-in read tool with image attachments). Blind sessions get the tool. Mid-session model switches re-evaluate visibility via `model_select`; the tool's appearance is announced once (when a model change activates it without its own notification), its disappearance is silent. Known edge: virtual models are judged by their own declared `input` capabilities — a virtual model that declares no image input while routing to a vision-capable sub-model gets aux vision. Registration mechanism note: the tool is registered at extension load and immediately stripped from the active set, because `defaultActive: false` does not exist in pi 0.86 (the SDK this repo type-checks against) — the steady state is equivalent to `defaultActive: false`, and visibility is set only by the gating sync point.
